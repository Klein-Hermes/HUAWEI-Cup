# Q1 最终收口与操作性主 Q 冻结任务说明（修订版）

> 适用阶段：Q1.1 小样本双人评分已完成，q_equal 与 q_huber 未被明显区分；Q1.2 冲突诊断已完成；Q1.3 已有 p-only 与 p+Q 运行结果。
>
> 目标：核查既有证据和数据依赖，在负责人明确操作性主 Q 后，生成 Q1 到 Q2/Q3 的正式接口并留下复现记录。不重新开展 Q1 建模，也不把操作性选择说成人工评审选出的唯一优胜模型。

---

## 1. 当前已知事实与边界

执行前以项目结果文件为准核对；如果文件数值与此处不同，先报告差异，不自行改写：

- 两份评分表由两位人工评审填写，项目负责人已确认评审人数和来源。
- 每份表完成 30 条；整体质量二次加权 Cohen Kappa 为 0.765146，评审间 Spearman 为 0.805995。
- 在 24 条 representative 样本上，q_equal 和 q_huber 对人工共识的 Spearman 均为 0.566692，本次核查未能区分两个候选。
- 两份表行序相同，且都对应 reviewer1 模板顺序；须记录预设的独立随机顺序协议未满足。
- 评审文本使用中文机译辅助版本；不得描述为评审人直接对英文原文完成验证。
- 是否两位评审在互不沟通的条件下独立评分，应依据可追溯记录确认。已确认有两位评审，不等于独立评分过程已核实；无证据时标记为“未核实”。
- Q1.2 是冲突诊断与稳健性证据，不与 Q1.1 作算术叠加。
- Q1.3 已有受限 p-only 与 p+Q 比较；不得根据已接触的评估集重新挑选模型，或声称存在稳定的普遍增益。
- 小样本核查不等于对 793 条文本完成全量人工效度验证。A2/A3 原文与映射缺口及其他上游限制继续披露。

## 2. 角色分工与阶段门

### 编程手可以做

- 核查仓库中已有的规则、结果、代码、参数和输入依赖；
- 校验候选结果未被改写，计算并记录文件哈希；
- 复核人工评分表及既有统计结果，不重新评分或改变统计口径；
- 追踪 Q1.3 实际使用的特征、候选分来源和输入文件；
- 在负责人作出明确选择后，生成正式接口、决策记录和复现清单。

### 编程手不能做

- 自行选择 q_equal 或 q_huber 作为主 Q；
- 根据人工评分修改权重、Huber 参数、抽样或模型；
- 将 Q1.2 冲突分直接加到 Q1.1；
- 为了得到 winner 而增加新的事后统计规则；
- 未经负责人/建模手确认就重跑 Q1.3；
- 把“操作性主 Q”描述成“人工评审证明的唯一最优 Q”。

### 两阶段执行门

**第一阶段：证据核查。** 不论负责人最终选择哪个候选，编程手都可先完成第 3 节，并提交核查结果。

**第二阶段：生成冻结接口。** 只有在存在可追溯的评审前预设规则，或负责人/建模手已留下明确的操作性选择记录后，编程手才能生成带唯一 q_operational 的正式接口。未收到选择时必须暂停在待决状态。

## 3. 第一阶段：核查既有证据，不做模型选择

### 3.1 核查评审前是否存在候选选择规则

在项目文件与可核验的 Git 历史中搜索 q_equal、q_huber、主 Q、默认 Q、下游接口、candidate_selected、operational Q 及相关选择规则。

只接受能证明在评分结果产生前已经存在的证据，例如已提交的 Git commit、带可靠时间记录的冻结配置或评审前生成的报告。普通文件修改时间不能单独证明规则在先；当前对话中的回忆也不能替代项目内可追溯证据。不得根据当前结果倒推预设规则。

生成核查记录，回答：

- PRESET_RULE_FOUND：true / false；
- 如为 true：记录候选、选择条件、证据文件、commit（如有）、可核验时间和具体位置；
- 如为 false：说明未找到合格证据，不推测或补写历史规则。

### 3.2 固定并核验既有 Q1.1 结果

- 记录 q_equal、q_huber 及人工评分分析结果的原始路径、版本、行数和 SHA-256。
- 确认本任务没有改变 q_equal、q_huber、人工评分和既有 Q1.1/Q1.2/Q1.3 结果。
- 引用已经计算的统计量；不重抽样、不重新评分、不更换统计口径。
- 如核验值与既有报告不一致，列出差异并暂停，不覆盖历史结果。

人工核查允许表述：

> 小样本双人评分核查已完成，但存在评分表顺序协议偏差；本次人工结果未能明显区分 q_equal 与 q_huber。

不得表述为“人工盲评选出了唯一最优 Q”或“人工验证证明某个候选更优”。

### 3.3 核查 Q1.3 对 Q 的真实依赖

不得只凭特征名称（例如 Q_covered(p)）判断是否依赖最终主 Q。必须检查并记录：

- p+Q 特征的实际公式及对应代码位置；
- 它读取的文件、列、映射表和参数；
- q_equal、q_huber 或领域质量映射是否参与特征计算；
- 当前既有 Q1.3 实验实际覆盖了哪些候选及设置；
- 相关输入和输出的 manifest、版本和哈希。

按核查结果填写：

- Q1.3_RERUN_REQUIRED = false：现有结果与候选选择无关，或现有实验已经包含负责人最终选中的同一候选和设置；不重跑，报告匹配证据。
- Q1.3_RERUN_REQUIRED = true_pending_approval：最终选择会改变模型输入，且现有实验没有覆盖该输入；停止，不重跑，提交差异供建模手/负责人决定是否做最小重跑。
- Q1.3_RERUN_REQUIRED = undetermined：依赖关系或结果清单无法核清；停止正式冻结并说明缺少的证据。

如果现有实验分别比较了 q_equal 和 q_huber，负责人选中的候选已在实验内，则不因选择操作主 Q 而重复训练，只需标明对应结果。若 Q1.3 使用由 p 和领域质量映射构造的特征，仍须沿完整数据链确认领域质量取值是否来自 q_equal/q_huber；不能仅凭“由 p 派生”跳过核查。

### 3.4 第一阶段交付与暂停条件

第一阶段至少交付：

- 评审前选择规则核查记录；
- Q1.1 人工核查结果及限制摘要；
- q_equal/q_huber 未改写的哈希核验；
- Q1.3 数据依赖与重跑判定报告。

若 PRESET_RULE_FOUND 为 false 且负责人尚未明确选择操作性主 Q，机器状态必须为：

- status = PENDING_PROJECT_OWNER_DECISION
- operational_q = null
- formal_interface_generated = false

此时不得生成正式下游接口，不得报告 Q1 已完成冻结。可提供待负责人填写的决策模板，但不能代填候选。

## 4. 第二阶段：负责人决定后生成操作性主 Q

负责人/建模手应在可追溯的决策记录中填写：

- 操作性主 Q：q_equal 或 q_huber；
- 选择依据：评审前预设规则，或负责人当前作出的透明操作性选择；
- 决策人及日期；
- 另一候选作为敏感性对照；
- 确认本次人评没有区分两候选，不把操作选择宣称为人工验证胜出。

若存在可核验的评审前规则，编程手按该规则落盘并引用证据。若不存在，编程手必须等待负责人选择，不得代选。

负责人决定后，编程手只从原候选结果中提取已选值，不重新训练、计算权重或改写候选数据。将操作性主 Q 标记为：

- selection_basis = preset_rule；或
- selection_basis = project_operational_choice。

不得把第二种写成“预注册选择”。

## 5. 正式下游接口与候选审计文件分开

### 5.1 样本级正式接口

生成 results/q1_final/q1_final_quality.csv，供 Q2/Q3 读取。只包含正式计算所需字段，例如：

- sample_id
- q_operational
- q_version
- 如下游确有需要，加入 source_domain

不得在正式计算接口中暴露 q_equal、q_huber 或 q_sensitivity，以免 Q2/Q3 再次自行挑选候选。

### 5.2 候选审计文件

另生成 results/q1_final/q1_candidate_audit.csv。其中可保留 sample_id、q_equal、q_huber、q_operational、q_sensitivity、q_version 和来源信息，供审计与敏感性分析使用。该文件不是 Q2/Q3 的默认计算入口。

### 5.3 行数、映射和缺失值

- 说明接口对应的样本范围、主键、行数和唯一性检查结果。
- 不因生成接口而伪造映射、补值或填充缺失；缺失继续保留并报告。
- q_operational 必须能逐行追溯到原候选值。
- 如来源映射或样本覆盖不完整，明确记录覆盖范围，不得把局部覆盖描述为全量覆盖。

### 5.4 领域级接口

只有当 Q2/Q3 确实需要领域级 Q，且项目已有明确、可追溯的聚合公式和分母规则时，才生成 results/q1_final/q1_final_domain_quality.csv。编程手不得自行发明领域聚合规则。若当前没有已批准的聚合定义，省略该文件，并在决策报告中说明。

- results/q1_final/q1_q13_consistency_check.md

- 另一候选如何保留；

- Q1.2 的诊断角色，不与 Q1.1 算术合并；
- Q1.3 实际输入、依赖关系及是否需要重跑；
- 样本覆盖、映射缺口、字段语义等仍存在的限制。

- 未收到负责人选择：status = PENDING_PROJECT_OWNER_DECISION，operational_q = null；

- review_order_protocol_deviation = true；
- q12_added_to_q_score = false；

不得在示例配置中预填 q_equal 或 q_huber，避免被误当成已批准决定。

复现清单至少记录输入和输出文件 SHA-256、候选结果哈希、人工评分文件哈希、代码 commit（如有）、脚本路径、运行命令、Python 环境、q_version 和生成时间。清单应能区分“证据核查阶段”和“负责人决定后的接口冻结阶段”。

## 7. 不覆盖范围

所有新增文件写入 results/q1_final/。保留并不得覆盖：

- q_equal、q_huber 原始候选及其计算结果；
- Q1.1、Q1.2、Q1.3 既有结果；

- 既有分析报告、manifest 和复现材料。

如需修订既有状态说明，新增带日期的补充记录，不静默改写历史结论。

## 8. 验收标准

### 第一阶段（不依赖负责人选择）

- 评审前规则核查有可追溯证据或明确报告未找到；
- q_equal/q_huber 和人评结果哈希核验通过；
- 人工核查结论、评审顺序偏差和译文限制均如实记录；
- Q1.3 真实特征依赖和重跑状态有代码及输入依据；
- 若负责人尚未选主 Q，状态停在 PENDING_PROJECT_OWNER_DECISION，未生成正式接口。

### 第二阶段（负责人已选择后）

- q_operational 与被选候选逐行一致，原候选未改变；
- 正式接口与候选审计表分开，Q2/Q3 默认只能读取唯一 q_operational；
- 缺失、映射覆盖、主键唯一性、行数和哈希核验通过；
- Q1.3 是否重跑的结论与实际依赖、已有候选覆盖一致；需要重跑时未经批准未执行；
- 冻结状态标记为 FROZEN_WITH_LIMITATIONS；
- 报告没有声称人工核查选出了唯一优胜候选。

只有第二阶段通过后，工程状态才能描述为：

> Q1 已完成受限范围的操作性冻结；主 Q 是按照可追溯的评审前规则或项目负责人的透明操作性决定确定的。小样本双人核查未能明显区分 q_equal 与 q_huber，不能声称人工验证证明主 Q 显著优于另一候选。

如果只完成第一阶段，应描述为：

> Q1 既有计算和证据核查已完成，操作性主 Q/正式下游接口仍待项目负责人决定；Q1 尚未完成操作性冻结。
