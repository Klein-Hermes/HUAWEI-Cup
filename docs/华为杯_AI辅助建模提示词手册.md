# 华为杯 AI 辅助建模提示词手册

> 用法：按阶段复制一段提示词到 Codex 或 Claude Code；将 `<...>` 替换为真实信息。每段只推进当前阶段，检查结果后再进入下一段。本文是操作模板，不是赛题答案，也不代替当届官方规则。

## 0. 先确定怎么分工

本手册以已安装的 `math-modeling`（XiaoMa）为主流程：建模手 → 编程手 → 论文手。`analytics-data-analysis` 负责独立的数据探索与清洗建议；`mathmodel-studio` 只在选题、模型选型或图表方案需要第二意见时局部调用。`python-code-reviewer`、`robustness-checker`、`completeness-auditor`、`consistency-auditor` 和 `quality-assurance-auditor` 用于审查。两套主流程不要同时接管项目进度。

本项目约定：`data/raw/` 放题目原件与原始数据，`data/processed/` 放派生数据，`src/` 放可运行代码，`notebooks/` 放探索笔记，`results/` 放计算结果，`figures/` 放 XiaoMa 要求的候选图，`docs/` 放本手册和团队决策记录。XiaoMa 自身规定的 `题目分析报告.md`、`术语表格.md`、`results/复现清单.json`、`完整论文.docx` 等路径仍按其 Skill 执行。不要为了迁就本目录约定而改掉它的固定交付物路径。

```text

目标竞赛：中国研究生数学建模竞赛（华为杯）；年份/届次：<填写>；题号：<填写或待定>。
我是新手。请先用通俗中文说明当前阶段要回答什么、需要哪些输入、判断标准是什么，再执行。每次只完成我指定的阶段，不自动进入下一阶段。
题目、附件和 data/raw/ 只读；派生数据另存 data/processed/。保留已有文件，修改前检查现状；关键模型取舍、异常值删除、指标口径和结论范围交我决定。
只用真实题面、真实数据和实际运行结果；任何缺失材料、无法核验的引用、未执行的命令、未通过的门禁都明确标出。每轮结束给出：新增/修改文件、证据路径、实际运行的命令与退出码、未解决问题、下一步建议。
当届官方规则、模板、截止时间、数据使用与 AI 使用要求以可核验的官方来源为准；不要把 Skill 内的往届经验写成当届规则。
```

### 总体推进顺序

```text
赛前环境/规则检查 → 题目与附件盘点 → 数据画像 → 候选方案 → 人工拍板
→ XiaoMa 建模手定稿/M1 → 编程最小闭环/P1 → 全量求解与出图/P2
→ Python 审查 → 稳健性/灵敏度 → 论文证据大纲/W1
→ Word 论文草稿/W2 → 完整性与一致性审查 → 综合 QA → 团队人工核对与提交
```

若某个阶段发现前提错误，带着具体证据退回相应阶段。模型或数据改变后，重跑受影响的代码、结果、图表和审查；论文里的旧数字不能继续沿用。

## 1. 比赛开始前：环境、规则与交付链

适合赛前或刚拿到题目时使用。此阶段不猜题、不建模。

```text
请为当前华为杯项目做一次赛前/开赛检查。先读取 README.md、environment.yml、requirements-base.txt 和项目目录。检查 Python 环境、必要的文档/绘图工具能否使用；只报告已有事实，不先安装所有可能依赖。

请从当届比赛官网或我提供的官方文件核验：竞赛名称与届次、开始和截止时间及其时区、题目与附件发布位置、论文和附件提交格式、匿名要求、页数/模板约束、外部数据与 AI 工具使用要求。每项给出官方来源、适用年份、核验时间；找不到的标“待核验”。

使用 math-modeling 时先读取其 SKILL.md、使用指南.md 及真实竞赛的截止时间协议。尽早用最小真实样例验证“代码运行 → 图表导出 → Word/PDF 渲染 → 提交文件检查”的链路，并提出第一个可保存的 Checkpoint V1 计划。此轮仅交付检查结果和时间安排，不写论文正文。
```

验收：你能说清楚“什么时候截止、交什么、现在哪个环节跑不通”。官方规则未核验前，后续排版要求只能标为暂定。

## 2. 收到赛题：只做题目与附件盘点

把题目、附件及官方说明放进项目后使用。不要直接让 AI 写完整论文。

```text
使用 XiaoMa 的 math-modeling Skill，当前只进入“建模手”阶段。读取当前项目中的赛题、全部附件及当届官方说明，先列出已读文件和未找到的文件。逐问提取：原题要求、需要回答的结论、输入数据、输出形式、约束、单位、问题之间的依赖、可检验的成功标准。

先给我一份审题清单和疑点清单，用通俗中文说明哪些地方有多种理解。对不明确的题意不要自行拍板；指出不同理解会怎样改变模型。暂时不要写代码、清洗原始文件或写论文。完成必要的数据初查后，再按建模手规定维护《题目分析报告.md》和《术语表格.md》；不要额外宣称建模阶段已通过 M1。
```

验收：每一问都对应清楚的“要回答什么”和“如何判定答到了”，附件没有漏读。

## 3. 数据探索：调用 analytics-data-analysis

若附件有 CSV、Excel、时间序列或其他表格数据，在模型选型前使用。`analytics-data-analysis` 的示例代码只作为示范；缺失值、异常值必须依赛题和数据含义处理。

```text
使用 analytics-data-analysis 对本题附件做探索性数据分析，并与 XiaoMa 建模手已经整理的每问目标对齐。请先检查所有相关数据文件是否可读，建立“文件 → 工作表/字段 → 单位 → 时间/空间范围 → 对应子问题”的数据字典。

对每个相关数据集报告行列数、字段类型、缺失值及其分布、重复/不可能值、异常值、分组样本量、量纲、时间排序和可能的数据泄漏。对关键变量做必要的分布图或关系图，并用一句话解释每张图帮助判断什么。

本轮先做画像和清洗方案，不直接删行、填补、标准化或修改 data/raw/。请比较至少两种合理处理方式（如果只有一种合理方式则说明原因），列出各自对后续模型的影响和验证办法。我确认处理规则后，再把可复现的处理代码放 src/，派生数据放 data/processed/，数据质量报告放 results/，记录原始与派生行数、转换步骤和输入文件哈希。
```

验收：你知道数据能支持哪些题问、哪些字段不可靠、清洗会不会改变结论。原始附件保持不变。

## 4. 寻找建模方案：局部使用 mathmodel-studio

这一段用于获取第二意见。`mathmodel-studio` 自带完整的 stage/state 工作流；此处只请求它的“模型选型建议”局部入口，避免和 XiaoMa 同时维护两套比赛状态。

```text
请局部使用 mathmodel-studio 的华为杯研究生赛模型选型入口，只做每问候选方案比较，不启动完整五幕十步流程，不进入求解或论文写作。读取真实题目、XiaoMa 的《题目分析报告.md》《术语表格.md》以及已完成的数据画像。

每一问给出：建议主方案、可完成同一任务的简单基线、必要时的备选方案；各自的输入输出、核心假设、关键公式/约束、对现有数据的要求、计算成本、主要失败风险和验证方案。区分“题目直接给定”“文献可核验”“建模假设”“尚未验证”四种依据。若参考类似题，只借鉴问题结构和验证思路，不搬用历史题目的数值或结论。

把选择卡交给我拍板。若 Skill 的局部入口要求缺失的完整流程 state 或门禁，请如实说明当前只能提供咨询性比较，不能伪造已通过的 stage 或人工决策记录。
```

验收：候选模型真正回答题问，可利用手头数据运行；基线输出与主方案可比较。

```text
我决定本题的建模路线如下：

- Q2：主方案 <填写>；比较基线 <填写>；关键假设 <填写>。

- 数据清洗取舍及理由：<填写>。
```

## 6. 编程第一步：最小可运行闭环

先跑通一个真实输入到真实输出的短链路，再做耗时计算。XiaoMa 的编程手将这个门禁称为 P1。

```text
使用 XiaoMa 的 math-modeling“编程手”阶段。先读取已经确定的《题目分析报告.md》《术语表格.md》、人工路线决定和真实附件。选择 Python 实现，按当前模型实际需要检查依赖；不要一次安装无关库。

本轮只构建最小可运行闭环：从 data/raw/ 读取一个真实输入，经已批准的预处理与核心模型，输出一个可核验的真实结果到 results/。同时实现一个能回答同一题问的基线，定义两者共同的评价指标。记录命令、随机种子、参数、输入规模、运行时间与退出码。请实际运行，并报告数值范围、单位和约束是否合理。

按编程手要求执行 P1 独立质检。未通过时先修复或把模型合同问题交回建模手；暂不全量扫描参数、不批量出正式图、不写论文。
```

验收：同一命令从项目根目录能实际运行，输入能追溯到结果，主方案与基线可比较。

## 7. 全量求解、结果整理与复现

```text
P1 通过后，继续使用 XiaoMa“编程手”完成全部子问题。保留数据读取、预处理、主方案、基线、评价指标和导出结果的可运行代码。每问分别输出最终答案所需的表格、误差/约束检查和简短解释；区分真实计算结果、估计、外推与假设。

如结果违反约束、单位不对、无法复现或与基线比较口径不同，请停下定位问题，不用文字圆过去。实际运行全部代码，按 Skill 生成 results/复现清单.json，含输入哈希、随机种子、依赖版本、关键参数和唯一复现命令。完成后执行编程阶段应有的 P2 复验；若图表尚未完成，则如实标记 P2 仍待完成。
```

验收：每一问有可复核的结果表和明确的结论；同一代码可重跑得到一致或解释得通的随机结果。

## 8. 图表：先确定结论，再生成与审图

图表属于编程手阶段，论文手只选择和引用已验证图。图的数量与导出检查按所用 Skill 的要求执行，同时以当届官方规则为准。

```text
继续使用 XiaoMa“编程手”，加载其 tools/figure/SKILL.md。先列“题目子问 → 要表达的结论 → 结果表/数据路径 → 合适图型 → 论文拟用位置”的图表计划。每张图先写一句核心信息，再根据变量类型、量纲和比较目的选图，不为了凑数量画重复图。

按编程手规范生成原始数据、模型运行过程、最终结果三类候选图，并覆盖所有子问题；生成至少一张与真实模型和代码一致的总体流程图。保留可运行的绘图代码。正式图按 Skill 导出 SVG 和高分辨率 PNG，执行 figure_audit.py 的 strict 覆盖检查，并实际查看彩色及灰度预览，在论文预计大小下检查裁切、重叠、字体、图例、单位和误导性的坐标轴。

将每张拟入文的图与其计算来源、图注和正文主张关联。若任何图的数据、参数或模型已改变，重生成该图并重新审查。完成后补跑受影响的 P2 门禁。
```

验收：读者不看正文也能从图题、坐标、单位理解图；图和结果表使用同一次有效运行的数据。

## 9. Python 代码专项审查

该 skill 原生要求方法卡、代码计划、人工决策与运行摘要。当前以 XiaoMa 为主流程时，先做真实文件映射；没有的证据要说明缺口。

```text
使用 python-code-reviewer 审查当前项目实际运行的 Python 代码。先把它需要的方法决定、模型说明、数据画像、代码计划和运行摘要映射到项目中真实存在的文件；列出映射表与缺失项。不要凭空创建“已批准”方法卡、决策 ID 或通过记录。

请实际执行必要代码，按 syntax、input_contract、method_alignment、reproducibility、output_contract 五类检查。额外检查：数据泄漏（按实体/时间分组是否跨训练与验证、预处理是否先看了测试集）、异常值处理、目标函数和约束实现、随机种子、路径、单位、边界条件、数值稳定性、基线是否可比。每个问题给出文件位置、复现证据、影响和修复建议。

本轮只审查，不修改代码。需要修复时，我会另行要求最小修复、重跑结果与受影响的门禁。若缺少审查前提，只报告受限审查，不给 PASSED。
```

修复时使用：

```text
请根据上一次 python-code-reviewer 的具体发现作最小修复。保留原始数据；不要未经我确认改变模型含义或指标口径。修改后重跑受影响的代码、结果表和图表，并更新复现清单；重新执行相应审查，比较修复前后关键数值。
```

## 10. 稳健性、灵敏度与局限性

```text
使用 robustness-checker 检查当前已批准、已实际运行的主模型和基线。先列出每问最影响结论的假设、参数与数据风险，并声明要检验的结论。根据问题选适用实验：参数/权重扰动、不同随机种子、合理的数据切分、缺失/异常值处理、约束容量变化、基线比较、排序稳定性、误差与不确定性等；不机械全部执行。

在看到结果前说明扰动范围、评价指标及其理由。实际运行、保存实验代码与机器可读结果；逐问报告结论保持稳定、仅在某些条件下成立，还是失效。阈值若在事后才提出，标为探索性，不能伪装成事前标准。发现不稳定时列出调整、回退或收窄论文主张的选项交我决定。

如 Skill 所需的 method card、probe summary、run summary 或人工决策记录在本工作区不存在，请列出可对应的真实证据及缺口；不要填造不存在的前置门禁。
```

验收：核心结论经得起与题目风险相称的扰动，或清楚写明成立范围。

## 11. 论文前的证据大纲

XiaoMa 论文手要求先过 W1，再开始长篇正文。生成物只是论文草稿，队伍需要人工核对和改写。

```text
先执行论文手的 W1 证据大纲质检；未通过时返回建模手或编程手补证据，不用文字编造结果。此轮不要生成完整论文。
```

## 13. 完整性与一致性终审

zhnnky 的审查模块原生使用它自己的 `rigor_profile`、manifest、决策账本、冻结数字和 G1–G5 门禁。XiaoMa 不一定生成同名文件。应先做真实证据映射；不具备原生前提时，可进行明确标注范围的专项检查，但不能虚称该模块原生全流程门禁 `PASSED`。

### 13A. 逐问完整性检查

```text
使用 completeness-auditor 做 submission 阶段检查，并额外做题目逐问对照。请从原题逐条提取必须回答的要求，为每条建立“论文位置 → 定量结果/图表 → 对应代码和数据 → 是否明确回答”的矩阵，区分已回答、只有方法没有结果、结果没有解释、完全漏答。

同时检查本 Skill 要求的证据是否存在、语义足够且未过期；允许把 XiaoMa 的真实产物映射为可说明的等价证据，但要列明差异。缺失的 manifest、冻结数字、代码审查或其他原生前提不能凭空补成“通过”。输出每项缺口、修复责任人、影响的子问及可以实际给出的审查结论。
```

### 13B. 跨媒介一致性检查

```text
使用 consistency-auditor 的 final 模式检查所有子问题。以真实运行结果表和已记录的人工作出决定为依据，逐一比对论文摘要/正文/结论中的数字与单位、公式与代码、参数与约束、图表数据和图注、符号表、文件路径、引用、稳健性结论。

检查结果是否因代码或数据更新而过期。每个不一致项指出“权威源在哪里、论文或图表哪里用了不同值、应由谁修复”。审查阶段不要自行改论文或代码。若 Skill 期望的 frozen_numbers.json 或决策账本不存在，指出可以验证与无法验证的范围，不从论文反推权威数字，也不虚报 final PASSED。
```

两个审查发现问题后，先修复对应源文件，重跑受影响的结果与图表，再复查；不要只改论文数字。

## 14. 最后综合 QA 与人工交接

```text
请在完整性与一致性审查完成并解决阻断项之后，使用 quality-assurance-auditor 做最终综合检查。读取前两份审查及真实代码、结果表、图表、引用来源和实际渲染的论文，不只相信摘要报告。

检查：每问是否回答、模型选择与人工决定是否一致、代码和结果是否可复现、主要结论是否有基线与稳健性证据、图表是否真实且可读、引用是否存在、摘要与正文是否一致、当届官方模板和提交要求是否已核验、AI 使用披露是否符合已核验规则。列出阻断与非阻断问题、证据路径和修复责任人。

如 zhnnky 原生所需的 submission profile、G1–G5 或审查产物没有建立，请给出 NOT_RUN 或受限审查结论，并解释缺口；不要为了“全绿”捏造门禁通过。此轮只审查，不替团队点击提交。
```

团队最后人工确认：通读题目和全文，亲自核对关键公式、代码输出、全部图表、引用、匿名信息、官方格式与提交文件；按当届规则处理 AI 辅助内容。由团队完成最终提交和平台成功回执确认。

## 最重要的三条检查原则

1. **题目要求对照**：每问都有明确结果和结论；“用了模型”不等于“回答了题目”。
2. **计算证据对照**：论文数字、图和结论来自实际运行的同一有效版本；修改上游后重跑下游。
3. **官方规则与团队责任**：Skill 内置模板和历史案例仅供参考；以当届官方规则为准，AI 产物需团队人工核对与改写。
